# Модуль мерч-кодов Catalist

Версия модуля: 2.3.0 · Обновлено: 2026-09-28

Рабочий адрес: https://code.catalist.world · Основной сайт: https://catalist.world (Tilda, без изменений)

---

## 1. Назначение и результат

Модуль добавляет к продукции Catalist серийную маркировку:

- **оператор производства** на code.catalist.world генерирует и сохраняет серийные номера изделий;
- **покупатель** на той же странице проверяет подлинность изделия и один раз регистрирует его на себя;
- **QR-код на сертификате** ведёт на `https://code.catalist.world/СЕРИЙНЫЙ-НОМЕР` — страница открывается сразу с результатом проверки.

Основной сайт catalist.world остаётся на конструкторе Tilda и не затрагивается: модуль живёт на отдельном поддомене того же VPS, где уже работает телеграм-бот из этого репозитория.

## 2. Архитектура

Один VPS, три сервиса docker compose:

| Сервис | Что делает | Порты | Данные |
|---|---|---|---|
| `bot` | телеграм-бот приёма заявок (существующий, без изменений) | нет входящих (long polling) | том `bot-data` |
| `merch` | FastAPI + SQLite: номера, проверка, журнал, дашборд | 8000 — только внутри docker-сети | том `merch-data`: база `merch.db` и бэкап ключа `serial-key.backup.json` |
| `caddy` | reverse-proxy, автоматический HTTPS (Let's Encrypt) для `MERCH_DOMAIN` | 80/443 наружу | тома `caddy-data`, `caddy-config` (сертификаты) |

```
          Интернет
    ┌────────┴─────────────────────────────────┐
    │ https://code.catalist.world              │ Telegram API (исходящее)
    ▼                                          ▼
┌────────────────── VPS · docker compose ──────────────────────┐
│                                                              │
│  caddy (80/443, авто-HTTPS) ──▶ merch (FastAPI + SQLite,     │
│  тома: caddy-data,              порт 8000 внутри сети)       │
│        caddy-config             том: merch-data              │
│                                 (merch.db,                   │
│                                  serial-key.backup.json)     │
│                                                              │
│  bot (телеграм-бот, long polling) — том: bot-data            │
└──────────────────────────────────────────────────────────────┘
```

Конфигурация прокси — `deploy/Caddyfile`; домен подставляется из переменной `MERCH_DOMAIN` (`.env`).

## 3. Серийный номер

Формат: **8 знаков Crockford Base32** — алфавит без I, L, O, U; при вводе похожие знаки исправляются автоматически (I/L→1, O→0, U→V), регистр не важен.

Семь знаков несут 35 бит полезной нагрузки:

| Поле | Бит | Диапазон | Смысл |
|---|---|---|---|
| `type` | 5 | 32 | тип изделия |
| `color` | 6 | 64 | цвет |
| `month` | 8 | 256 | месяц выпуска, отсчёт с января 2026 (хватает до 2047 года) |
| `place` | 4 | 16 | площадка производства |
| `seq` | 12 | 4096 | порядковый номер издания |

Восьмой знак — контрольный, вычисляется в поле Галуа GF(32): гарантированно ловит одиночную опечатку и перестановку двух соседних знаков.

Payload перед кодированием перемешивается несбалансированной сетью Фейстеля (4 раунда, половины 18/17 бит) на **128-битном ключе** — соседние номера внешне не связаны, восстановить поля без ключа нельзя. Ключ хранится только на сервере (база + файл-бэкап); в интерфейсе показывается лишь его отпечаток вида `XXXX-XXXX`.

Ядро (`merch/app/serials.py`) — точный порт логики прототипа hallmarksuite.tsx: совместимость бит-в-бит закреплена 64 эталонными векторами, сгенерированными из исходного JS-кода (`merch/tests/vectors.json`).

## 4. Гарантии уникальности и журналы в БД

Хранилище — SQLite в режиме WAL (`merch-data:/app/data/merch.db`).

**ledger** — журнал выданных номеров. Два ограничения на уровне БД: `PRIMARY KEY (code)` и `UNIQUE (slot)`, где слот — комбинация `type-color-month-place-seq`. База физически не даст сохранить один номер или одну комбинацию дважды — в том числе при гонке одновременных запросов с двух рабочих мест. Важные правила:

- **Generate (preview) ничего не пишет** — слот занимает только **Save (confirm)**;
- удаление записи освобождает слот — комбинацию можно выдать заново.

**verify_log** — все проверки номеров: время, нормализованный код, статус (`issued` / `not_issued` / `mismatch` / `malformed`), IP. Это полная история проверок каждого сертификата. Хранение — `MERCH_VERIFYLOG_DAYS` дней (по умолчанию 365), устаревшие записи вычищаются при старте сервиса.

**audit_log** — действия персонала: сохранение номера, удаление записи и очистка журнала, правка каталога, входы, смена ролей. По каждой записи — кто, когда, что сделал.

**users / sessions** — учётные записи Google и серверные сессии. Сессия — cookie `merch_session` (HttpOnly), срок жизни 12 часов.

**schema_migrations** — версия схемы БД. Миграции применяются автоматически при старте: база от сборки 1.x обновляется на месте, без потери данных и ручных действий.

## 5. Ролевая модель

Четыре штатные роли и публичный доступ:

| Действие | admin | config | production | ledger | публично |
|---|:-:|:-:|:-:|:-:|:-:|
| Генерация и сохранение номеров (issue preview/confirm/next-seq) | ✓ | — | ✓ | — | — |
| Каталог: просмотр | ✓ | ✓ | ✓ | — | — |
| Каталог: правка (PUT /api/catalog) | ✓ | ✓ | — | — | — |
| Журнал: просмотр (GET /api/ledger) | ✓ | — | ✓ * | ✓ | — |
| Журнал: экспорт CSV | ✓ | — | — | ✓ | — |
| Удаление записи / очистка журнала | ✓ | — | — | — | — |
| Пользователи, статистика, логи проверок и действий (/api/admin/*) | ✓ | — | — | — | — |
| Проверка номера (verify) | ✓ | ✓ | ✓ | ✓ | ✓ |
| Регистрация владельца (register) | ✓ | ✓ | ✓ | ✓ | ✓ |

\* журнал доступен и роли production — для контроля собственной выдачи.

Публичные операции ограничены по частоте на IP: verify — 30/мин, register — 10/мин, служебные эндпоинты — 60/мин. Лимиты настраиваются переменными `MERCH_VERIFY_PER_MIN`, `MERCH_REGISTER_PER_MIN`, `MERCH_ISSUE_PER_MIN`.

**Способы входа персонала:**

1. **Google-аккаунт** — OAuth 2.0 code flow (настройка: `docs/google-oauth-setup.md`). Роль назначает администратор в дашборде. Bootstrap: email из `MERCH_ADMIN_EMAILS` при первом входе автоматически получает роль admin. Прочие новые пользователи получают роль `none` («ожидает назначения») и не имеют доступа, пока администратор не выдаст роль.
2. **PIN-коды переходного периода** — заголовок `X-Pin`: `MERCH_PRODUCTION_PIN` → роль production, `MERCH_ADMIN_PIN` → admin. Полная совместимость со сборкой 1.x.

**Покупателю аккаунт не нужен**: регистрация владельца — анонимная форма. Если Google настроен, на форме есть кнопка «заполнить из Google» (`mode=buyer`) — имя и email подставляются в форму из профиля, staff-аккаунт при этом не создаётся.

## 6. Интерфейсы

С 2.3.0 сайт разнесён на **три адреса** — каждой аудитории своя ссылка:

| Адрес | Для кого | Что на странице |
|---|---|---|
| `/` | покупатели | проверка номера + регистрация владельца |
| `/factory` | подрядчики-изготовители | выдача номеров, журнал, печать сертификатов |
| `/admin` | администраторы | дашборд всей системы |

Бургер-меню и футеры показывают служебные разделы только тем ролям, которым
они открыты: гость и покупатель видят лишь клиентские пункты; Factory
появляется у production/ledger/admin, Admin dashboard — у admin/config/ledger
(роль берётся из сессии Google или PIN текущей вкладки). Прямой переход по
адресу всегда возможен, но встречает экран входа — данные закрыты ролями API.

**Клиентская страница** `https://<поддомен>/` — только **Check**: проверка номера (четыре статуса: изделие подлинное; формат корректный, но номер не выпускался; расшифровка не совпадает с журналом; номер набран с ошибкой). При подлинном номере показывается **фотография изделия в его цвете** и — один раз на номер — форма регистрации владельца.

**Страница производства** `https://<поддомен>/factory` — вход по PIN или Google, две вкладки:

- **Serial** — выдача: площадка → изделие → цвет → месяц → номер издания, с подсказкой следующего свободного номера. **Generate** — предпросмотр без записи, **Save** — запись в журнал, затем **Print certificate**.
- **Register** — журнал выданных номеров; у каждой записи кнопка **Certificate**.

**Сертификат подлинности** (по макету заказчика): логотип, Special edition, название изделия, № издания / тираж, серийный номер в гравированных ячейках, фото изделия, QR на страницу проверки, подпись-инструкция и две подписи. Формат берётся из каталога (`sheet` у изделия):

- **A5** (Balloon Cat) — полноформатный лист, печать на бумаге A5;
- **A7** (Guardian of Cyprus) и **A8** (Guardian of Cyprus S) — «бирки»: печатаются на листе **A4** в натуральную величину (74 и 52 мм по ширине), пунктирная рамка — линия реза.

Кнопка Print certificate открывает системный диалог печати; масштаб и размер страницы (`@page`) подставляются автоматически, лист всегда помещается на одну страницу. В диалоге печати должна быть включена печать фона (Background graphics), иначе тёмные ячейки номера выйдут белыми — современный Chrome/Safari включают это для сертификата сам (print-color-adjust).

**Дашборд** `https://<поддомен>/admin` — шесть разделов:

- **Overview** — статистика, отпечаток ключа, версия модуля;
- **Users** — роли и деактивация учётных записей;
- **Catalog** — редактор каталога изделий, цветов и площадок. Предупреждение: индексы позиций зашиты в выпущенные номера — позиции с выпущенными номерами нельзя переставлять и удалять, только выключать;
- **Journal** — журнал с экспортом в CSV и печатью сертификатов;
- **Discounts** — скидки покупателей, отметка «использована»;
- **Logs** — журнал проверок и журнал действий персонала.

**Глубокая ссылка** `https://<поддомен>/XXXXXXXX` — страница с автопроверкой номера; именно на неё ведёт QR-код сертификата.

## 8. Развёртывание (runbook)

Быстрый путь — скрипт `deploy/deploy.sh` (шаги 2–4 он выполняет сам, включая
создание `.env` из шаблона, проверку PIN-ов, сборку, запуск и health-check):

```bash
git clone -b claude/merch-code-generator-module-ng1tmq https://github.com/DmitryMednov/Catalist.git
cd Catalist
./deploy/deploy.sh   # первый запуск создаст .env и попросит его заполнить
nano .env            # PIN-ы, домен, токены бота
./deploy/deploy.sh   # соберёт, запустит и проверит
```

Тот же скрипт используется и для обновлений: `./deploy/deploy.sh` подтягивает
свежую версию ветки, пересобирает и перезапускает сервисы (миграции БД
применяются автоматически). Ниже — те же шаги вручную.

1. **DNS.** У регистратора/в DNS-панели создать A-запись `code` (или выбранного поддомена) → IP VPS; TTL по умолчанию. Проверка: `dig code.catalist.world +short` или `nslookup code.catalist.world` — должен вернуться IP сервера. Записи основного домена и `www` не трогать — они смотрят на Tilda.
2. **Настройки.** На сервере: `git pull` рабочей ветки, затем `cp .env.example .env` и заполнить:
   - `BOT_TOKEN`, `ADMIN_CHAT_IDS`, `REVIEW_CHAT_ID` — как раньше (бот);
   - `MERCH_DOMAIN` — поддомен из шага 1;
   - `MERCH_PRODUCTION_PIN`, `MERCH_ADMIN_PIN` — оба обязательны, не короче 4 знаков и разные; иначе служебные функции модуля отключены (ответ 503);
   - `MERCH_ADMIN_EMAILS=mednovdmitry@gmail.com` — первый администратор;
   - `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` — по инструкции `docs/google-oauth-setup.md`; можно заполнить позже — до этого вход работает по PIN;
   - `MERCH_SERIAL_KEY` — оставить пустым: ключ сгенерируется при первом старте.
3. **Запуск.** `docker compose build && docker compose up -d`. Порты 80 и 443 должны быть свободны и открыты в фаерволе.
4. **Проверка.** Открыть `https://<домен>/healthz` (ответ `{"ok": true}`), затем на вкладке Serial выпустить тестовый номер, проверить его на вкладке Check и удалить в журнале.
5. **Сертификат.** Caddy получает и продлевает сертификат Let's Encrypt автоматически. Если поддомен создан только что — подождать распространения DNS и обновить страницу.

### Стартовая партия и очистка тестовых данных (`app.seed_batch`)

Ключ шифрования серийных номеров никогда не покидает сервер, поэтому партии
кодов выпускаются **на сервере** одной командой (из каталога репозитория):

```bash
docker compose exec merch python -m app.seed_batch          # показать план
docker compose exec merch python -m app.seed_batch --yes    # выполнить
```

Что делает запуск с `--yes` (сентябрь 2026 — партия запуска):

1. удаляет все тестовые данные: журнал номеров, скидки, кабинеты покупателей,
   лог проверок (Google-пользователи, их роли и audit-журнал сохраняются);
2. записывает каталог запуска из `merch/app/catalog_seed.py`
   (Crystal White, форматы A5/A7/A8, фотографии, тиражи 25 и 20);
3. выпускает партию со сквозной нумерацией внутри тиража — каждый
   «№ / тираж» существует в одном экземпляре: Balloon Cat — № 001–025
   подряд по пяти цветам из тиража 25 (Dubai); серия Guardian — общий
   тираж 20: большая фигурка № 001–010, маленькая № 011–020 (Cyprus);
   месяц — текущий;
4. печатает список кодов и сохраняет его в `/app/data/issued-codes.txt`
   (посмотреть позже: `docker compose exec merch cat /app/data/issued-codes.txt`).

Повторный запуск с `--no-reset` ничего не удаляет и пропускает уже занятые
номера — дублей не будет. Состав партии задан в `BATCH_PLAN` того же файла.

## 6a. Личный кабинет покупателя и скидка за регистрацию

Появилось в 2.1.0. Сценарий покупателя:

1. Покупатель сканирует QR сертификата → страница проверки, номер подтверждён.
2. Заполняет форму регистрации (или «заполнить из Google»). В момент регистрации:
   - в таблицу `discounts` записывается **скидка `MERCH_DISCOUNT_PERCENT`%** (по умолчанию 10) с кодом вида `CAT-XXXX-XXXX` — одна на фигурку, статус `active`;
   - на почту уходит **письмо-уведомление**: изделие, номер издания, скидка и кнопка входа в кабинет (magic-ссылка);
   - браузер сразу получает cookie кабинета — кнопка «Open my collection» ведёт в `/my` без пароля.
3. **Кабинет `/my`**: все фигурки, зарегистрированные на этот email (фото, цвет, № издания, месяц, площадка, серийник), и по каждой — карточка скидки с **QR-кодом**. Вход в кабинет: ссылка из письма (можно запросить повторно по email; ответ сервиса одинаков для любых адресов — базу не перебрать) или Google (`mode=cabinet`; staff-учётка при этом не создаётся).
4. **На кассе** покупатель показывает QR → кассир открывает `/d/<код скидки>`: крупный вердикт «VALID — N% OFF» с изделием и именем владельца, либо «ALREADY USED». Администратор отмечает использование в дашборде (вкладка **Discounts**) — после этого страница показывает «использована».

Хранение: таблица `buyers` (email → хэш токена кабинета; выдача новой ссылки гасит старую), таблица `discounts` (код скидки, фигурка, email, процент, статус, флаг отправки письма). Удаление записи журнала не удаляет выданную скидку; при повторной выдаче того же слота и повторной регистрации скидка на код остаётся прежней (дубль не создаётся).

**Настройка почты.** Два варианта:

- **Вариант А — Brevo HTTPS-API (рекомендуется на DigitalOcean).** Хостинги часто блокируют исходящие SMTP-порты 25/465/587 на уровне сети (ошибка в логах — `[Errno 101] Network is unreachable`); API работает по 443 и не блокируется. Настройка: аккаунт на brevo.com (бесплатно 300 писем/день) → **Senders** → добавить и подтвердить адрес отправителя → **Settings → SMTP & API → API Keys** → создать ключ. В `.env`: `MERCH_BREVO_API_KEY=xkeysib-...` и `MERCH_SMTP_FROM=<подтверждённый адрес>`. При заданном ключе SMTP-настройки не используются.
- **Вариант Б — классический SMTP** (если провайдер не режет порты): `MERCH_SMTP_HOST`, `MERCH_SMTP_PORT` (587), `MERCH_SMTP_USER`, `MERCH_SMTP_PASSWORD`, `MERCH_SMTP_FROM`, `MERCH_SMTP_SECURITY` (`starttls` | `ssl` | `none`).

После правок — `docker compose up -d merch`. Результат каждой отправки виден в `docker compose logs merch | grep -i mailer`. Пока SMTP не настроен: скидка и кабинет работают, письма не уходят (в дашборде колонка Email показывает, отправлено ли письмо по каждой скидке); ссылку в кабинет покупатель в этом случае получает кнопкой сразу после регистрации.

**До настройки DNS.** Ссылки в письмах и QR-коды скидок собираются из публичного адреса модуля. Пока домен не работает, укажите в `.env` временный адрес по IP — иначе письма и QR будут вести на ещё не существующий домен:

```bash
MERCH_PUBLIC_URL=http://<IP сервера>:8080
```

После включения домена удалите эту строку и выполните `./deploy/deploy.sh`. Secure-флаг cookie кабинета и сессий подстраивается под схему адреса автоматически.

Дополнительные эндпоинты 2.1.0:

| Метод | Путь | Доступ | Назначение |

### Если DNS пока недоступен

Модуль можно развернуть и проверить до настройки домена: caddy дополнительно
слушает порт **8080** по чистому HTTP, интерфейс открывается по адресу
`http://<IP сервера>:8080`. Это временный технологический доступ: трафик не
шифруется, поэтому не пользуйтесь на нём боевыми PIN-ами дольше необходимого
(после перехода на https PIN-ы легко сменить в `.env`). Когда A-запись будет
создана, от сервера ничего не требуется — Caddy сам выпустит сертификат для
`MERCH_DOMAIN`, и https-адрес заработает без перезапуска. После этого удалите
проброс `8080:8080` из `docker-compose.yml` и блок `http://:8080` из
`deploy/Caddyfile`, затем `docker compose up -d caddy`.

## 9. Интеграция с Tilda

- На основном сайте добавить пункт меню или кнопку **«Проверка подлинности»** → `https://code.catalist.world`. В Tilda это любой блок с кнопкой и внешней ссылкой — правок кода не требуется.
- QR-коды на новых сертификатах ведут на `https://code.catalist.world/НОМЕР`.
- Старые QR вида `catalist.world/НОМЕР`: Tilda не проксирует произвольные пути, варианты:
  - (а) оставить как есть — откроется страница 404 Tilda; на неё стоит добавить ссылку на проверку;
  - (б) в настройках Tilda включить редирект с несуществующих страниц: 404 → `https://code.catalist.world`. Тогда старые QR приводят на страницу проверки, номер вводится вручную.

Рекомендация: вариант (б) плюс печатать новые сертификаты уже с адресом поддомена.

## 10. Бэкапы и сопровождение

**Ключ шифрования** — самое ценное:

```bash
docker compose cp merch:/app/data/serial-key.backup.json ~/backups/
```

Хранить **отдельно** от бэкапа базы: потеря ключа делает нечитаемой всю выпущенную маркировку; утечка ключа вместе с базой даёт возможность подделки номеров.

**База данных** — скрипт `deploy/backup.sh`: делает консистентный снимок работающей базы (VACUUM INTO), складывает в `~/catalist-backups/merch-ДАТА.db` и удаляет копии старше 14 дней (настраивается `CATALIST_BACKUP_KEEP_DAYS`).

```bash
./deploy/backup.sh        # разовый бэкап
# ежедневный бэкап в 03:20 — установка cron одной командой:
(crontab -l 2>/dev/null; echo "20 3 * * * $HOME/Catalist/deploy/backup.sh >> $HOME/catalist-backups/backup.log 2>&1") | crontab -
```

Периодически скачивайте папку бэкапов с сервера (`scp -r root@СЕРВЕР:~/catalist-backups ~/`) — копия на том же диске не спасает от гибели самого сервера.

**Обновление:** `git pull` → `docker compose build` → `docker compose up -d` — миграции схемы применяются сами.

**Откат:** `git checkout <тег>` → `build` → `up -d`; базу восстановить из бэкапа, если миграция новой версии несовместима со старым кодом (см. CHANGELOG.md).

**Логи:** `docker compose logs -f merch` и `docker compose logs -f caddy`. **Мониторинг:** внешняя проверка `https://<домен>/healthz`.

**Ротация PIN:** поправить `.env` → `docker compose up -d merch`. **Ротация ключа шифрования штатно не предусмотрена** — смена ключа сделала бы все выпущенные номера нечитаемыми.

**Персональные данные.** При регистрации владельца в ledger сохраняются имя, дата рождения и email покупателя. Удаление записи журнала удаляет и эти данные.

## 11. Версионность и совместимость

- Версия модуля — semver, задаётся в `merch/app/version.py` (`APP_VERSION = "2.0.0"`) и отдаётся в `/api/status`.
- Схема БД версионируется таблицей `schema_migrations`; миграции только аддитивные (новые таблицы и колонки), поэтому сборка 2.x читает данные 1.x без конвертации.
- PIN-вход сборки 1.x сохраняется.
- Правила нумерации: **MAJOR** — несовместимые изменения API или схемы; **MINOR** — новые возможности; **PATCH** — исправления. Перед обновлением на новый MAJOR бэкап базы обязателен.
- История релизов — `CHANGELOG.md` в корне репозитория.

## 12. Что сознательно отложено

- Печать сертификатов на сервере — пока выполняется в прототипе.
- Отдельные PIN на каждую площадку (per-site PIN).
- Письма покупателям после регистрации изделия.
- Переход на внешнюю БД (PostgreSQL) — при росте нагрузки; текущий SQLite для ожидаемых объёмов достаточен.
